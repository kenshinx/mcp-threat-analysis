# 数据库表结构说明

本文档按"谁写入 / 谁读取 / 起什么作用"的角度描述 `sql/001_schema.sql` 中
每张表在三层管线（`static_analysis` / `semantic_analysis` / `risk_scoring`）
中的职责。表按数据流位置而非建表顺序列出。

## 一句话视图

```
servers + package_versions + tools          ← 实体（L0 discovery / L1 canonicalization 写）
        │
static_analysis 读源码 → 写 findings + static_summaries
        │
semantic_analysis 读 static_summaries + tools → 写 findings (+ tool_capabilities + llm_calls)
        │
risk_scoring 读 findings + server_popularity → 写 servers.risk_* + server_risk_history + triage_queue
```

跨层接口仅通过两张表传递：`findings`（所有 detector 的输出账本）和
`static_summaries`（L2 抽出的结构化摘要供 L3 复用）。`semantic_analysis`
不重新扫描源代码——它读 L2 写好的 summary。

---

## 主体实体

### `servers`
全平台中心实体，每个被分析的 MCP server 一行。

- **写入**：L0（discovery）、L1（canonicalization）；`risk_scoring` 反写
  `risk_score` / `risk_priority` / `risk_updated_at` / `weights_version`。
- **读取**：所有层 FK 到它。
- **关键列**：`canonical_name UNIQUE NOT NULL` 是去重键；`status` 为
  `active` / `removed` / `quarantined`，`removed` 表示该 server 已从 registry
  下架。

### `package_versions`
同一个 server 在 npm / PyPI 等 registry 上的历史版本元信息（发布时间、
artifact SHA、发布者、依赖快照）。供 L4（temporal / diff 层）追溯供应链
事件，例如 postmark 风格的 rug pull。

- **写入**：L0 周期同步。
- **读取**：L4；当前管线未直接消费。

### `tools`
server 暴露的每个工具的 *声明*，来自 `tools/list` snapshot。

- **写入**：L0。
- **读取**：`semantic_analysis` 的全部 detector：
  - `char_layer` 检查 `description` 中的隐藏字符（ZWSP / ANSI escape）
  - `shadowing` 通过 `description_emb`（pgvector 1536 维）跨 server 找语义近邻
  - `schema_code_alignment` 将 `input_schema` 与 L2 抽出的代码 IO 行为对比
  - `tpa_text_rules` / `tpa_llm` 基于 `description` 文本判定工具投毒
- **关键列**：`description_emb VECTOR(1536)` 由 `semantic_analysis/embeddings/`
  生成，offline 缺省走 hash 编码器，`MTA_EMBEDDING_PROVIDER=openai` 时切到
  真实 embedding。

## 跨层接口（最重要的两张）

### `findings`
所有层共用的问题报告账本。`layer` 列区分来源：`static_analysis` /
`semantic_analysis` / `runtime_analysis` / `network_analysis`（后两者预留）。

- **写入**：所有 detector 通过 `common.persistence.upsert_findings()`。
- **读取**：
  - `semantic_analysis.tpa_text_rules` 会读 `static_analysis` 写入的 text-rule
    findings，再写一条带工具关联的 `semantic_analysis` 副本
  - `risk_scoring` 全部聚合输入
- **去重**：唯一部分索引
  `(server_id, detector, artifact_ref, evidence->>'evidence_key') WHERE status='active'`
  保证同一证据点不重复 active。重复写入时旧行被标 `superseded` 并通过
  `superseded_by` 指向新行。
- **状态机**：`active` / `suppressed` / `superseded` / `confirmed` /
  `false_positive`。仅 `risk_scoring/lifecycle.py` 修改 `status`，其他模块
  只插入 `active` 行。
- **更新触发器**：`findings_updated_at` 是 `risk_scoring` ingestor 轮询的信号
  源，每次写入或状态变更都会刷新 `updated_at`。

### `static_summaries`
`static_analysis` 把每次扫描抽出的结构化 summary 缓存到 `summary` JSONB。
按 `(server_id, version)` 主键。

- **写入**：`static_analysis/persistence.save_static_findings()`。
- **读取**：`semantic_analysis` orchestrator 在启动时载入此行作为分析输入。
- **summary 内容**：`tool_handlers`（每个工具的代码位置 / 局部 IO 调用 /
  字符串字面量 / 调用图）、`string_literals` / `hosts`、
  `declared_egress_domains`（来自 `server.json`）、`obfuscation_score`、
  `manifest_facts`（package.json / pyproject 元信息）、`sca_deps`。
- **设计意图**：`schema_code_alignment` 检测的最关键设计——LLM 调用看到
  的是结构化 summary，不是源代码 token，从而把成本和上下文窗口压到合理
  范围。

## semantic_analysis 内部表

### `tool_capabilities`
LLM 把工具描述 + schema 分类后的能力标签缓存。

- **写入**：`semantic_analysis/detectors/toxic_flow.py` 在能力分类 LLM 调用
  返回后写入。
- **读取**：toxic_flow 自身在重跑时用 `content_hash`（描述+schema 哈希）做
  缓存命中，避免每次重新调用 LLM。
- **键**：`tool_id PRIMARY KEY`，每个工具仅最新一次分类生效；`content_hash`
  变化即视为缓存失效。

### `llm_calls`
每次 LLM 调用的审计 + 缓存表。

- **写入**：`semantic_analysis/llm/client.py`。
- **读取**：成本监控（`tokens_in` / `tokens_out` / `cost_usd`）、重复调用
  去重（`prompt_sha` + `input_sha` 命中即取缓存而非再次发请求）、可追溯
  finding 来源（`finding_id` 关联回 `findings.id`）。
- **索引**：`(detector, model, prompt_sha, input_sha)` 是缓存命中的查询键。

## risk_scoring 内部表

### `server_risk_history`
每次 aggregator 重算后追加一行（`(server_id, scored_at)` 主键，append-only）。

- **写入**：`risk_scoring/aggregator.py`。
- **读取**：`/servers/{id}/risk/history` API；分数趋势分析；回归检测
  （新版本得分突然升高）。
- **关键列**：`findings_digest` 是参与本次评分的 finding 摘要，便于复盘。

### `triage_queue`
P0 / P1 server 的人工处置队列。

- **写入**：`risk_scoring/triage_router.py`，带 24 小时 debounce 防止反复
  enqueue 同一 server。
- **读取**：`/triage` API；L7 disclosure 从这里取处置工单。
- **状态**：`pending` / `in_review` / `resolved`，`resolution` 为
  `confirmed_malicious` / `confirmed_vuln` / `fp` / `duplicate`。

### `server_popularity`
流行度快照（npm 下载量、GitHub stars 等）。

- **写入**：L0 周期同步。
- **读取**：`risk_scoring/aggregator.py` 把 `pop` 作为最终分的乘子，使流行
  度高的 server 在同分情况下推到更高优先级。
- **关键列**：`raw JSONB` 保留各来源原始指标，便于权重调整。

---

## FK / 删除级联

所有非 `servers` 表都 `REFERENCES servers(id) ON DELETE CASCADE`：删除
`servers` 行会清除其全部 findings / summaries / tools / 历史记录。
`findings.superseded_by` 指向同表：旧 finding 被新 finding 取代时形成链路，
便于审计同一证据点的演进。

# L6 风险聚合与评分 · 系统设计

> 上位文档：[[恶意 MCP 检测可执行技术方案]] §8
> 目标读者：L6 层开发负责人

---

## 1. 职责与边界

### 1.1 职责

- 把 L2/L3/L4/L5 各层产出的 finding 聚合为 **server 级 risk_score**
- 跨层 / 跨 detector 信号交叉验证，对高一致性命中做 confidence boost
- 生成 **告警分级（P0/P1/P2/P3）** 与 triage 队列
- 提供 finding 生命周期管理（active / suppressed / superseded / confirmed / false_positive）

### 1.2 输入 / 输出

| 项 | 内容 |
|---|---|
| **输入** | `findings` 表所有写入事件（增量） |
| **输出 1** | `servers.risk_score` 更新；`server_risk_history` 时间序列 |
| **输出 2** | `triage_queue` 行（P0/P1） |
| **输出 3** | webhook / 队列消息（推给 L7 披露层） |

### 1.3 不在 L6 范围内

- 检测逻辑本身（属 L2/L3/L4/L5）
- 披露执行（属 L7）
- 用户配置 / 通知偏好（属 L7）

L6 是**纯数据聚合 + 评分 + 路由**，无 detector。

## 3. 子模块设计

### 3.1 ingestor

**触发方式**：
- 优先：监听 `findings` 表的 logical replication / CDC（Debezium 或 Postgres `LISTEN/NOTIFY`）
- 降级：每 60s 轮询 `findings WHERE updated_at > last_seen`

**幂等**：同 finding 多次进入 ingestor 不重复计分（按 `finding_id` 去重）。

**批量**：每 5 秒或 100 条 finding 触发一次聚合，避免每条 finding 都重算 server 风险分。

### 3.2 aggregator

主算法（基线，按主方案 §8.1）：

```python
SEVERITY_WEIGHTS = {"critical":10.0, "high":5.0, "medium":2.0, "low":0.5, "info":0.1}
DETECTOR_CLASS_WEIGHTS = {
    "L2:semgrep":          1.0,
    "L2:codeql":           1.2,
    "L2:secret":           1.5,
    "L2:sca":              0.8,
    "L2:manifest":         1.0,
    "L2:reputation":       0.6,
    "L2:obfuscation":      1.2,
    "L3:char":             1.5,
    "L3:tpa-rule":         1.2,
    "L3:tpa-llm":          1.5,
    "L3:shadowing":        1.0,
    "L3:schema-code":      2.0,
    "L3:toxic-flow":       1.5,
    "L3:untrusted":        0.8,
    "L4:version-diff":     2.0,
    "L4:remote-targeted":  3.0,
    "L4:namespace":        2.0,
    "L4:commit-anomaly":   1.5,
    "L5:dynamic-egress":   2.5,
    "L5:dynamic-fs":       2.0,
    "L5:protocol-anomaly": 1.5,
}

def aggregate(server_id) -> float:
    findings = active_findings_for(server_id)
    score = 0.0
    for f in findings:
        sw = SEVERITY_WEIGHTS[f.severity]
        dw = DETECTOR_CLASS_WEIGHTS[detector_class(f.detector)]
        score += sw * dw * f.confidence
    score = apply_cross_validation_boost(server_id, score)
    score = apply_popularity_factor(server_id, score)
    return min(100.0, score)
```

**popularity factor**（保持主方案 §8.1 现状，不在 L6 重构）：
```python
def apply_popularity_factor(server_id, score):
    pop = popularity.get(server_id)         # 0..1
    return score * (1 + pop)                # 1.0–2.0 倍率
```

**写入**：
- `servers.risk_score` 直接 update
- 同时 append `server_risk_history(server_id, scored_at, score, finding_count, top_findings_ref)`

### 3.3 cross_validator

按主方案 §8.3 的两条规则起步：

```python
RULES = [
  Rule(
    name="schema_code_corroborates_egress",
    require=[
      detector_eq("L3:schema-code-inconsistency"),
      detector_eq("L5:dynamic-egress"),
    ],
    boost=0.3,
  ),
  Rule(
    name="postmark-style",
    require=[
      detector_match(r"L4:version-diff:.*bcc.*"),
      detector_eq("L5:dynamic-egress"),
    ],
    boost=0.5,
  ),
]
```

**实现**：每次 aggregator 触发时，遍历 RULES，若 require 全部命中则在 score 上叠加 `boost * critical_weight`。

**扩展**：rule 配置化（YAML），不放代码内；运维可热加载。

### 3.4 triage_router

```python
def classify(server) -> Priority:
    findings = active_findings_for(server.id)
    if any(f.severity == "critical" and f.confidence >= 0.9 for f in findings):
        return "P0"
    if multi_detector_hit(findings, threshold=3) and max_severity(findings) >= "high":
        return "P0"
    if any(f.severity == "high" for f in findings):
        return "P1"
    if popularity_top_pct(server, 1) and max_severity(findings) >= "medium":
        return "P1"
    if any(f.severity == "medium" for f in findings):
        return "P2"
    return "P3"
```

| 等级 | 处置 |
|---|---|
| **P0** | 写入 `triage_queue(priority='P0')`，同时立即推送 L7 webhook（人工介入） |
| **P1** | 写入队列，24h 内人工 review |
| **P2** | 周报汇总；不主动告警 |
| **P3** | 仅入数据集 |

**去抖**：同 server 同优先级 24h 内不重复推送 webhook（除非升级）。

### 3.5 lifecycle

`findings` 表新增 lifecycle 字段（L6 owner，按主方案目前 schema 不含；先在 L6 落地必要的最小集合，避免影响 L2/L3 写入）：

```sql
ALTER TABLE findings
  ADD COLUMN status        TEXT NOT NULL DEFAULT 'active'
    CHECK (status IN ('active','suppressed','superseded','confirmed','false_positive')),
  ADD COLUMN status_changed_at TIMESTAMPTZ,
  ADD COLUMN superseded_by  UUID NULL REFERENCES findings(id),
  ADD COLUMN suppressed_reason TEXT NULL;
```

**状态转移**：
- `active`（默认）：新写入 → 进入聚合
- `suppressed`：人工标记 / FP 库自动匹配 → 不计分
- `superseded`：同 detector 同位置同 server 重写 → 旧的标记
- `confirmed`：triage 确认是真漏洞 / 真恶意
- `false_positive`：triage 确认误报 → 进 FP 库

**superseded 自动化**：L2/L3 重跑时，先把同 `(server_id, version, detector, evidence_key)` 的旧 finding 设为 `superseded`，再写新的。

### 3.6 weights

权重表加载策略：
- 默认值在代码内（上面的 `SEVERITY_WEIGHTS / DETECTOR_CLASS_WEIGHTS`）
- 可在 `config/l6_weights.yaml` 覆盖
- 修改权重生成新 `weights_version`；每条 `server_risk_history` 行记录所用 `weights_version`，便于审计 / 回放

### 3.7 popularity

输入来源：
- npm weekly_downloads / PyPI downloads / GitHub stars
- registry indexed_in 数量（Glama / Smithery / mcp.so / PulseMCP / official）

归一化：
```python
pop = min(1.0,
          0.4 * log10_norm(weekly_downloads, max=1e6)
        + 0.3 * log10_norm(stars, max=1e5)
        + 0.3 * (indexed_in_count / 5))
```

刷新：每天一次；缓存表 `server_popularity(server_id, pop, computed_at)`。

## 4. 数据契约

### 4.1 servers 表（既有，L6 写入字段）

```sql
-- 既有
risk_score REAL,
status     TEXT,
-- L6 新增
risk_priority   TEXT,    -- 'P0'/'P1'/'P2'/'P3'
risk_updated_at TIMESTAMPTZ,
weights_version TEXT
```

### 4.2 server_risk_history

```sql
CREATE TABLE server_risk_history (
    server_id       UUID,
    scored_at       TIMESTAMPTZ,
    score           REAL,
    priority        TEXT,
    finding_count   INT,
    findings_digest JSONB,   -- top-N finding 的 (detector, severity, confidence)
    weights_version TEXT,
    PRIMARY KEY (server_id, scored_at)
);
```

供 L7 输出趋势报告与回归。

### 4.3 triage_queue

```sql
CREATE TABLE triage_queue (
    id          UUID PRIMARY KEY,
    server_id   UUID,
    priority    TEXT,
    enqueued_at TIMESTAMPTZ,
    assignee    TEXT NULL,
    status      TEXT,        -- 'pending','in_review','resolved'
    resolution  TEXT NULL,   -- 'confirmed_malicious','confirmed_vuln','fp','duplicate'
    resolved_at TIMESTAMPTZ NULL,
    notes       TEXT NULL
);
```

人工 review 操作通过 API → 写 `resolution` → 反向调用 lifecycle 把对应 finding 标 `confirmed` / `false_positive`。

## 5. 性能与运行约束

| 项 | 目标 |
|---|---|
| 单 server 重算延迟（finding 写入到 risk 更新） | P50 < 10s |
| 全量服务器（10 万级）重算 | 后台批 < 1h |
| triage_queue 写入 → webhook 推送 | < 5s |

**重算触发**：
- 任一 finding 写入 / lifecycle 变更
- 权重 / 规则配置变更 → 全量重算（带版本号）
- popularity 每日刷新后增量重算

---

## 6. 错误处理

| 错误 | 处理 |
|---|---|
| 单 server 计算异常 | 记 ops，保留旧 score，下次重试 |
| popularity 数据缺失 | factor 默认 1.0（不放大） |
| weights 配置 yaml 解析失败 | 拒绝热加载，保留旧 weights |
| webhook 推送失败 | 至少 3 次重试 + DLQ |

## 8. 测试策略

| 类型 | 内容 |
|---|---|
| **单元测试** | 权重、cross_validator rule、triage classify 边界 |
| **回放测试** | 用历史 finding 数据集重跑 aggregator，断言 risk_score 与已记录值一致（用 weights_version 锁定） |
| **配置变更测试** | 修改权重 yaml → 全量重算 → 校验所有 server 重新评分 |
| **lifecycle 测试** | superseded / suppressed 状态对评分的影响 |

## 9. 开发顺序建议

1. `models` + `persistence` + `weights`（默认值）
2. `lifecycle`（DDL + status 转移 API）
3. `aggregator`（基础评分，无 cross-validation）
4. `ingestor`（轮询版优先，CDC 后置）
5. `popularity` 数据源接入
6. `cross_validator`（先硬编码，再配置化）
7. `triage_router` + `triage_queue`
8. `api/`（read-only view）
9. `server_risk_history` 写入 + 回放测试
10. webhook 推送（与 L7 联调）

## 10. 开放问题

- 权重表是否需要 per-detector 而非 per-class — 先按 class 起步，运行后看是否有 detector 需要单独调
- `aggregate` 当前是线性加和（已知会被多 detector 噪声放大）— 主方案评估中已记下，按"实际开发再优化"原则保留
- popularity factor 同时出现在 risk 与 triage — 是否拆分（risk 不放大、triage 放大）— 同上保留
- weights 修改的全量重算是否在 L6 内做、还是发任务给独立 worker — 看实际数据量决定
